## 1. 왜 만드는가

현재 홈 필터는 **브랜드 단위**(VISA / MASTER / JCB / AMEX)다.
브랜드로는 못 잡는 케이스가 실제로 있다.

- 선불카드(트래블월렛·트래블로그)는 **호텔 보증금 · 렌터카 · 주유소**에서 거절된다. 비자인데도 안 된다
- 일부 매장은 체크카드만 거부한다

그래서 **카드 상품 단위**로 등록받아야 한다.

동시에 이 기능이 수익구조의 전제다. 카드사에 팔 수 있는 데이터
("트래블월렛 유저 3천명이 도쿄에서 12% 거절")는 상품 단위 등록 없이는 나오지 않는다.

### 수익 로드맵 (2026-09-28 합의)

| 단계 | MAU | 수익원 | 월 예상 |
|---|---|---|---|
| 1. 데이터 채우기 | ~1만 | **0원 (의도적)** | 0 |
| 2. 검증 | 1만~10만 | 카드 발급 제휴 CPA | 15만~150만 |
| 3. 사업 | 10만+ | 카드사 B2B 데이터·제휴 | **보류 — 재검토 중** |

2026-09-28 추가: 카드사 상대 영업·투자 유치는 당분간 안 하기로 함. 3단계는 보류.
남는 수익원은 카드 발급 제휴 CPA · 여행 예약 제휴 CPS · 애드몹이고, 셋 다 붙여도 MAU 1만 기준 월 30만원이 천장이다.
**수익 모델 최종 확정은 아직.**

## 2. 등록 방식 — 사진 촬영 안 함

카드 실물 촬영 방식은 **채택하지 않는다.** 이유 3개.

1. 카드 사진에 번호·유효기간이 찍힌다 → PCI DSS 규제 대상, 플레이 심사 리스크, 유출 시 배상 책임
2. 사진으로 상품 구분이 안 된다. OCR이 읽는 건 로고까지 = "비자"까지만 → 지금 홈 필터와 동일, 얻는 게 없다
3. 클라우드 OCR은 호출당 과금 → 유지비 0원 원칙 위반

**채택: 목록에서 2번 터치.** 사진보다 빠르고 정확하다.

## 4. 데이터 구조 (Firestore)

```
users/{uid}
  myCards: ["twl_visa_prepaid", "shinhan_soltravel_master"]   // 상품 코드만

cardProducts/{productCode}          // 마스터 목록
  issuer: "트래블월렛"
  name:   "트래블페이 체크"
  brand:  "VISA"
  type:   "prepaid"                 // prepaid | debit | credit

reports/{reportId}                  // 제보
  storeId, productCode
  result: "ok" | "declined"         // declined 가 핵심
  createdAt, uid
```

카드번호·유효기간·CVC는 **어떤 필드에도 저장하지 않는다.**

## 5. 금지 사항

1. **카드번호 입력칸 만들지 않기.** 넣는 순간 PCI DSS 대상
2. **사진 업로드 없음** (2항 참조)
3. **등록 강제 금지.** 가입 시 요구하면 이탈. 마이페이지에서 원할 때만
4. **placeholder 사용 금지** (프로젝트 공통 규칙). 3단계 검색창도 라벨로 처리
5. **빈 화면 대비.** 데이터 0건에서 "내 카드만 보기"를 켜면 목록이 비어버린다
   → 초기엔 브랜드 기준으로 채워두고, 제보가 들어오면 상품 단위로 덮어쓴다

## 7. 초기 데이터 확보 전략 (2026-09-28 추가)

앱은 심사 중, 사용자 0명. 첫 데이터는 직접 깔아야 한다.
"서로 등록하고 검색하는" 구조라 빈 화면이면 등록도 검색도 안 일어난다.

### OSM 실측 결과 — 기대 이하

Overpass API로 직접 조회한 실제 수치 (2026-09-28).

| 범위 | `payment:visa` 건수 |
|---|---|
| 난바·도톤보리 일대 (관광 핵심) | **14건** |
| 오사카시 전역 | **164건** |

14건 중 자판기 3, 편의점 2. 실제 쓸 만한 식당·상점은 9곳.
**"OSM으로 300~500곳 깔기"는 오사카에서 불가능하다.** 일본 OSM 상점 데이터가 얇다.

전 세계 통계는 `payment:visa` 179,985 / `payment:mastercard` 173,808 / `payment:jcb` 23,395 (taginfo, 2026-09-27).

### 결정적 발견 — OSM에는 "안 됨"이 없다

조회된 14건이 전부 `=yes`다. **거절 정보가 한 건도 없다.**
OSM도 구글맵도 "이 가게 카드 됨"만 적는다.
여행자가 정작 알고 싶은 "여기 카드 안 됨"은 어디에도 없다.

→ 이게 해카의 자리다. 경쟁자가 없는 게 아니라 아무도 안 모으고 있어서 비어 있다.
→ [[수익구조]] 상 팔 수 있는 데이터도 이쪽뿐이다.

### 채우는 방법 — 체인점 일괄 등록

| 방법 | 확보량 | 평가 |
|---|---|---|
| OSM 그대로 | 164 | ✗ 너무 적음 |
| **체인점 일괄 등록** | 500+ | ⭕ 채택 |
| 본인 손입력 | 하루 100 | △ 정확도 낮음 |

일본 편의점·체인은 **전 지점 카드 정책이 동일**하다.
패미마·로손·세븐·스타벅스·맥도날드 등 브랜드 단위로 한 번 등록하면 지점 수백 개가 깔린다.
지점 좌표는 OSM에서 받아오면 된다.

**구조: 체인점으로 뼈대 → 개인 식당은 사용자가 채움.**
여행자가 실제로 궁금해하는 것도 개인 식당 쪽이라 역할이 맞는다.

### 미확인 배지 필수

직접 가보지 않고 깐 데이터는 반드시 표시한다.

```
이치란 라멘
🟢 비자 가능 · 미확인
   ↑ 아직 제보 없음. 확인해주시면 반영돼요
```

확인된 것처럼 보이게 하면 앱이 죽는다. 빈칸이 있어야 사람이 채운다.

### 1단계 목표 (숫자)

| 항목 | 목표 |
|---|---|
| 도시 | **1곳만** |
| 매장 | 300~500곳 |
| 제보 중 '거절' 비율 | 20% 이상 |
| 수익 | 0원 |

넓게 말고 깊게. 한 도시에서 "해카 켜면 다 나온다" 소리가 나와야 사람이 온다.

### 사람 모으기

"제보해주세요"는 안 먹힌다. 남 좋은 일이라서.
해카는 서로 등록하고 검색하는 구조이므로 **거래로 제시한다.**

> 해외에서 카드 안 돼서 당황한 적 있으시죠?
> 그런 가게들 모으는 지도 만들고 있어요.
> 본인이 겪은 곳 하나만 등록해주시면,
> 남이 등록한 수백 곳을 검색할 수 있습니다.

핵심은 **1개 넣고 수백 개 가져가는 거래**라는 점.

| 채널 | 이유 |
|---|---|
| 스레드 | 반응 빠름, 불평 글이 잘 퍼짐 |
| 트래블월렛·트래블로그 사용자 카페 | 거절 경험이 제일 많이 쌓인 곳 |
| 네이버 여행 카페 (도시별) | 막 다녀온 사람이 있음 |
| 오픈카톡 여행방 | **지금 현지에 있는 사람** — 즉시 확인 가능 |

보상은 현금 말고 데이터로. "제보 3건 = 그 도시 전체 목록 먼저 열람".

## 8. OSM 데이터 사용 시 처리

ODbL 라이선스. 데이터 판매·투자 유치를 안 하는 동안은 **출처 한 줄이면 끝**이다.

```
마이페이지 → 약관/정보 하단
"일부 매장 정보는 OpenStreetMap(ODbL) 기반입니다"
```

단, DB에 컬럼 하나는 지금 넣어둔다. 소급 불가.

```
source: "osm" | "chain" | "user"
```

나중에 데이터를 팔 일이 생기면 `user` 분만 골라낼 수 있어야 한다.
섞여 있으면 통째로 의심받는다.
